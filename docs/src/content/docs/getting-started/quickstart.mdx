Get Whatomate up and running in minutes using Docker or manual installation.

## Quick Start (Docker)

The fastest way to get started:

```bash
# Clone the repository
git clone https://github.com/trysoft-team/whatomate.git
cd whatomate
cp config.example.toml config.toml
cp .env.example .env  # Edit to set PostgreSQL credentials and timezone

# Start all services (PostgreSQL, Server)
make docker-up

# Access the application
open http://localhost:4747
```

<Aside type="note">
  The `.env` file is required by Docker Compose. It sets PostgreSQL credentials (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`) and the server timezone (`TZ`). Copy `.env.example` to `.env` and edit as needed. `.env` is gitignored, so your credentials stay local.
</Aside>

**Default login:** `admin@admin.com` / `admin`

<Aside type="caution">
  Change the admin password immediately after first login.
</Aside>

## Manual Installation

### Prerequisites

- Go 1.25+ (the module targets `go 1.25.0`)
- Node.js 20+ — only needed to build the frontend. CI builds it on Node 20; Vite 7 requires 20.19+ or 22.12+.
- A database — use the one you already run:
  - PostgreSQL — CI tests against 16, the Docker Compose file ships 17
  - MySQL 8.0.19+ or MariaDB 10.6+ — CI tests against MySQL 8.4 and MariaDB 10.6
  - SQLite — no server; the data lives in one file. Best for a single server.
- Redis 7 — optional (Redis 6+ works; `username` requires 6+ ACLs). Without it, whatomate uses a built-in store; see [`[redis]`](/whatomate/getting-started/configuration/#redis).

### Step 1: Clone and Configure

```bash
git clone https://github.com/trysoft-team/whatomate.git
cd whatomate
cp config.example.toml config.toml
```

### Step 2: Set Up the Database

Pick the database you already have and set `[database] driver` to match. Migrations create the tables on first start.

<Tabs>
  <TabItem label="PostgreSQL">
    ```bash
    psql -c "CREATE USER whatomate WITH PASSWORD 'whatomate123';"
    psql -c "CREATE DATABASE whatomate OWNER whatomate;"
    ```

    ```toml
    [database]
    driver = "postgres"
    host = "localhost"
    port = 5432
    user = "whatomate"
    password = "whatomate123"
    name = "whatomate"
    ```
  </TabItem>
  <TabItem label="MySQL / MariaDB">
    ```sql
    CREATE DATABASE whatomate CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
    CREATE USER 'whatomate'@'%' IDENTIFIED BY 'whatomate123';
    GRANT ALL PRIVILEGES ON whatomate.* TO 'whatomate'@'%';
    ```

    ```toml
    [database]
    driver = "mysql"   # also for MariaDB
    host = "localhost"
    port = 3306
    user = "whatomate"
    password = "whatomate123"
    name = "whatomate"
    ```
  </TabItem>
  <TabItem label="SQLite">
    Nothing to install or create; the file is created on first start.

    ```toml
    [database]
    driver = "sqlite"
    path = "./whatomate.db"
    ```
  </TabItem>
</Tabs>

See [Database Setup](/whatomate/getting-started/configuration/#database-setup) for TLS, version requirements and the trade-offs of each.

### Step 3: Setup Redis (optional)

Skip this step unless you run several API servers or separate worker machines. To use Redis, start it and set `[redis] host` in `config.toml`:

<Tabs>
  <TabItem label="macOS">
    ```bash
    brew install redis
    brew services start redis
    ```
  </TabItem>
  <TabItem label="Ubuntu/Debian">
    ```bash
    sudo apt install redis-server
    sudo systemctl start redis
    ```
  </TabItem>
  <TabItem label="Docker">
    ```bash
    docker run -d -p 6379:6379 redis:alpine
    ```
  </TabItem>
</Tabs>

### Step 4: Start Backend

```bash
# Install Go dependencies
go mod download

# Run migrations and start server
make run-migrate
```

### Step 5: Start Frontend

Open a new terminal:

```bash
cd frontend
npm install
npm run dev
```

### Step 6: Access Application

| Service | URL |
|---------|-----|
| Frontend | http://localhost:3000 |
| API | http://localhost:4747 |

**Login:** `admin@admin.com` / `admin`

<Aside type="caution">
  Change the admin password immediately after first login via the Profile page.
</Aside>

## Production Build

For production, build a single binary with embedded frontend:

```bash
make build-prod
./whatomate
```

This creates a self-contained binary—no separate frontend server needed. Without a config file it starts the [setup wizard](#first-run) at http://localhost:4747.

To build for another system, set `GOOS`/`GOARCH`, for example `GOOS=linux GOARCH=amd64 make build-prod`. `make release-snapshot` builds every release archive into `dist/`.

### Linux install script

On a Linux server, one command installs or upgrades whatomate and gets it ready for the [setup wizard](#first-run):

```bash
curl -fsSL https://raw.githubusercontent.com/trysoft-team/whatomate/main/scripts/install.sh | sudo bash
```

The script:

1. Downloads the latest release for the server's CPU (`amd64`, `arm64` or `armv7`), checks it against `checksums.txt` and installs it to `/usr/local/bin/whatomate`.
2. Offers to install `ffmpeg`, `opus-tools` and `espeak-ng` for calling and spoken IVR greetings (apt, dnf, yum, zypper, pacman or apk).
3. Creates a `whatomate` system user and the folders `/etc/whatomate` (config), `/var/lib/whatomate` (data) and `/var/whatomate` (uploads and call audio).
4. When the server's public IP isn't on any of its network interfaces (AWS, GCP, Azure), offers to set it for call media (`WHATOMATE_CALLING__PUBLIC_IP` in the service).
5. Writes a systemd service (`whatomate.service`) that runs as the `whatomate` user and starts at boot.
6. Detects Apache, nginx or Caddy, asks for your domain and adds a site that proxies it to whatomate, WebSockets included. With Apache or nginx it then offers a free Let's Encrypt certificate through certbot; Caddy gets one by itself. If no web server is installed, it offers to install nginx.
7. Opens the firewall with ufw, firewalld or iptables (whichever is active): TCP 80 and 443 behind the proxy, otherwise TCP 4747, plus UDP 10000–10100 for calls. It never turns a firewall on.
8. Starts whatomate and prints the setup wizard link, with your domain when the proxy is set up.

Run it again to upgrade: it replaces the binary and restarts the service, and keeps your config and service file.

| Option | Effect |
|---|---|
| `--version X.Y.Z` | Install this release instead of the latest |
| `--domain NAME` | Domain for the reverse proxy, e.g. `chat.example.com` |
| `--proxy NAME` | `apache`, `nginx`, `caddy` or `none` |
| `--email ADDRESS` | Email for the Let's Encrypt certificate |
| `--no-tls` | Don't request a certificate |
| `--no-firewall` | Don't change firewall rules |
| `--no-voice` | Don't install ffmpeg, opus-tools and espeak-ng |
| `-y`, `--yes` | Use the defaults instead of asking |

Pass options after `bash -s --`, for example:

```bash
curl -fsSL https://raw.githubusercontent.com/trysoft-team/whatomate/main/scripts/install.sh | sudo bash -s -- --domain chat.example.com --email you@example.com
```

<Aside type="note">
  Point the domain's DNS A record at the server before running the script, so the certificate can be issued. On a cloud server, also allow the same ports in the provider's firewall or security group.

  **Virtualmin:** Virtualmin manages the Apache sites, so the script doesn't add one. It prints the directives to paste into the domain's **Web Configuration → Edit Directives** (in both the port 80 and 443 sites).
</Aside>

### Prebuilt Binaries

Each [GitHub release](https://github.com/trysoft-team/whatomate/releases) includes archives for:

| OS | Architectures |
|---|---|
| Linux | `amd64`, `arm64`, `armv7` (Raspberry Pi 2 and later, 32-bit) |
| macOS | `universal` (one binary for Apple Silicon and Intel) |
| Windows | `amd64`, `arm64` |
| FreeBSD | `amd64`, `arm64` |

Extract the archive and run `whatomate`; the [setup wizard](#first-run) creates the config. It needs a database: SQLite works out of the box, or point it at a PostgreSQL or MySQL/MariaDB server. Voice features also use `ffmpeg`, and the IVR text-to-speech uses Piper, `espeak-ng` and `opus-tools`. The Docker image includes all of these; on a bare server, install them yourself.

<Aside type="note">
  **macOS:** release binaries are signed and notarized when the project's Apple credentials are configured. If macOS says the developer can't be verified, the binary was built without them; allow it under System Settings → Privacy & Security, or run `xattr -d com.apple.quarantine ./whatomate`. Install the dependencies with Homebrew: `brew install ffmpeg espeak-ng opus-tools`, plus `postgresql@16` or `mysql` unless you use SQLite or an existing server.
</Aside>

### Homebrew

On macOS and Linux, install the release binary from the project's tap:

```bash
brew install trysoft-team/tap/whatomate
```

This also installs `ffmpeg` and `opus-tools`. The database is not installed automatically, so you can point Whatomate at a server you already run, or use SQLite, which needs no server. Redis is optional.

Then run `whatomate` and finish the [setup wizard](#first-run). On macOS it saves the config to `$(brew --prefix)/etc/whatomate/config.toml`. Upgrade with `brew upgrade whatomate`.

### How Releases Are Published

Every push to the `master` branch of [trysoft-team/whatomate](https://github.com/trysoft-team/whatomate) runs the ~1,100 core tests on PostgreSQL (`make test-release`), then tags the next patch version and publishes the archives above plus the Homebrew cask. Pushes that only touch docs or Markdown are skipped. A minor or major bump is a manual run of the **Release** workflow on `master`, or a `vX.Y.Z` tag pushed by hand.

The cask is written to `trysoft-team/homebrew-tap` only when the `HOMEBREW_TAP_TOKEN` secret is set: a fine-grained token with **Contents: read and write** on that repository. Set the `HOMEBREW_TAP_OWNER` repository variable to publish to a tap under a different owner.

## First run

Start whatomate:

```bash
whatomate
```

With no config file, whatomate opens a setup wizard in your browser at
http://localhost:4747. The address it opens, and the ones it prints in its
log, end in `#token=…`: a one-time key that only this run of whatomate
accepts. When you reach the wizard another way (on a server without a
desktop, or from another machine), open the **full** URL from the log,
including the key; without it the wizard asks for the link or key.
The wizard:

1. checks the system (folders, disk, memory, port, internet, clock, audio tools);
2. asks which database to use: SQLite (nothing to install), PostgreSQL or MySQL;
3. creates your organization and admin account (or restores a backup, see
   [Restore from a backup](#restore-from-a-backup));
4. writes the config file and starts whatomate on the same port.

Then log in with the admin account you created in the setup wizard, or, after
a restore, with an account from the backup.

:::caution
Until setup is finished, anyone who has the setup link with its key can
complete it. Keep the link private (it is in whatomate's log), run the first
setup on a private network or behind a firewall, then expose whatomate.
:::

To set up again, delete the config file (`whatomate config path` shows where
it is) and start whatomate. The wizard only uses an empty database, so also
delete the SQLite file (or drop the PostgreSQL/MySQL database), or choose a
new one.

### Restore from a backup

To move an existing whatomate to this server, choose **Restore from a backup**
on the Welcome page instead of **Start fresh**. The wizard checks the system
and asks for the database as usual, but instead of creating an admin account
it restores a backup made in
[Settings → Backup & Restore](/whatomate/features/backup-restore/):

1. Pick the backup:
   - **Upload a backup** sends a `.zip` from your computer (up to 10240 MB).
     It is kept in the `backups` folder of the data folder (shown on the
     System check step), so it later shows up in Settings → Backup & Restore.
   - **On this server** lists the `.zip` backups already in that `backups`
     folder, or takes the full path to any backup `.zip` on the server.
2. Check the summary: when and with which whatomate version the backup was
   made, the database it came from and the one it is going into, how many rows
   and tables it holds, and its files.
3. Optionally paste the old server's `encryption_key` (from its `config.toml`)
   into **Old encryption key**. The wizard checks it against the backup and
   shows "Matches the backup"; a key that does not match blocks the restore.
   If you leave it blank, the restore still works and a new key is generated,
   but saved WhatsApp access tokens, AI provider keys and SSO client secrets
   must be entered again after signing in. A backup without encrypted secrets
   needs no key.
4. Press **Restore and finish**. The page shows the progress: preparing the
   database, checking the backup, loading data, linking records, putting
   files back and saving settings.

The database must have no users: use an empty one (one left behind by an
unfinished **Start fresh** attempt of this wizard, or by a restore into the
same database that stopped before it finished, is also accepted). No admin
account is created and no safety backup is taken. When the restore finishes,
sign in with an account **from the backup**.

The backed-up files go into the `uploads` and `audio` folders: under
`/var/whatomate` on Linux when that folder can be created, otherwise (and on
macOS and Windows) in the data folder. If loading the data fails, nothing is kept and no config file is
written; fix the problem and try again. If the data is restored but some files
cannot be put back, the data and config are kept: the page says what went
wrong and offers **Continue to sign in**.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| `connection refused` (database) | Ensure the database is running: `pg_isready` (PostgreSQL) or `mysqladmin ping` (MySQL/MariaDB) |
| `connection refused` (redis) | Ensure Redis is running (`redis-cli ping`), or comment out `[redis]` to use the built-in store |
| `database does not exist` | Create it: `createdb whatomate` (PostgreSQL) or `CREATE DATABASE whatomate CHARACTER SET utf8mb4` (MySQL/MariaDB) |
| `permission denied` | Check database user/password in `config.toml` |
| `port already in use` | Change port in `config.toml` or stop conflicting service |
| Frontend can't reach API | Ensure backend is running on port 4747 |
